## Contrato observado

Derivado de `api/app/main.py`; no existe `docs/ENDPOINTS.md`, por lo que estos comportamientos son observados y no contratos acordados.

| Método y ruta | Contrato observado | Evidencia |
|---|---|---|
| `GET /api/tasks` | Requiere `Authorization: Bearer <token>`; acepta `owner` opcional y devuelve una lista de tareas con `id`, `title`, `description`, `status`, `owner`, `priority` y `createdAt`. | `api/app/main.py:17`, `api/app/main.py:67-75` |
| `POST /api/tasks` | Requiere token; recibe un objeto JSON sin modelo Pydantic declarado, aplica valores por defecto a campos y responde `201` con la tarea creada. | `api/app/main.py:77-88` |
| `GET /api/summary` | Requiere token; acepta `owner` opcional y devuelve `owner`, `total`, `byStatus` y `highPriorityOpen`. | `api/app/main.py:90-106` |
| `POST /api/requirements` | Requiere token; recibe `file` multipart y responde `201` con `owner`, `fileName`, `storedAt` y `size`. | `api/app/main.py:108-112` |
| `GET /api/backend-health` | Requiere token; consulta la URL configurada por `AUTH_HEALTH_URL` (o el valor predeterminado) y devuelve `requestedBy`, `status` y `body`. | `api/app/main.py:115-121` |

El token observado se decodifica como Base64 y contiene cuatro segmentos separados por `|`; se comprueba la cantidad, el secreto fijo y que la expiración no haya pasado. No se observa validación de firma, emisor ni audiencia. Evidencia: `api/app/main.py:14`, `api/app/main.py:17-25`.

## Discovery adicional — api (2026-11-03, post-refactor de H-API-01 a H-API-05)

Investigación realizada sobre el código actual de `api` (después de las
resoluciones ya registradas arriba), sin modificar código. Base de
verificación: lectura de `api/app/main.py`, `api/app/uploads.py`,
`api/app/security.py`; ejecución de `pip-audit -r requirements.txt` y de
`pytest --cov=app --cov-report=term-missing` dentro de `api/.venv` (32
pruebas, 100% de cobertura de líneas y ramas en el estado actual). Todos los
hallazgos siguientes quedan marcados **CANDIDATO** y pendientes de revisión
humana; no se crearon issues ni se modificó código de producción.

### CORS con origen comodín y credenciales habilitadas
- Estado: CANDIDATO
- Evidencia: `api/app/main.py:38-44` configura `CORSMiddleware(allow_origins=["*"], allow_credentials=True, ...)`. En el paquete instalado (`api/.venv/Lib/site-packages/starlette/middleware/cors.py:34-36`) se confirmó que `allow_all_origins and allow_credentials` fuerza `preflight_explicit_allow_origin=True`, es decir, Starlette refleja el `Origin` de la petición en vez de aplicar una restricción real cuando ambas opciones están activas a la vez.
- Impacto: cualquier origen puede recibir respuestas con credenciales incluidas; si en el futuro se introduce autenticación basada en cookies/sesión (hoy es un header `Authorization` manual), esta configuración anularía por completo el aislamiento de origen. Incluso sin cookies, es una configuración insegura por defecto que no distingue orígenes confiables de no confiables.
- Prioridad propuesta: media (no hay explotación directa confirmada con el esquema de auth actual, pero es una mala configuración de defensa en profundidad fácil de corregir).
- Contrato potencialmente afectado: ninguno de los contratos de `docs/ENDPOINTS.md` cambia; el ajuste es de configuración de middleware, no de forma de petición/respuesta.
- Cómo validarlo: prueba de integración con `TestClient` enviando `Origin: https://evil.example` y verificando que la respuesta de preflight/[`Access-Control-Allow-Origin`] no refleje ese origen cuando se restrinja la lista; revisar con el equipo qué orígenes de `web` deben quedar permitidos explícitamente.

### `starlette` con CVEs conocidos, sin pin ni mitigación
- Estado: CANDIDATO
- Evidencia: `pip-audit -r api/requirements.txt` (ejecutado 2026-11-03 sobre `api/.venv`) reporta 10 vulnerabilidades conocidas para `starlette 0.50.0` (`PYSEC-2026-161`, `PYSEC-2026-2281`, `PYSEC-2026-2280`, `PYSEC-2026-249`, `PYSEC-2026-248`), con versión corregida hasta `1.3.1`. `api/requirements.txt` fija `fastapi==0.128.2` pero no fija ni restringe `starlette`, que llega como dependencia transitoria.
- Impacto: igual que con `urllib3`/`python-multipart` en H-API-05, el riesgo concreto de cada CVE no se verificó caso por caso en este discovery (solo se confirmó que `pip-audit` los reporta); requiere contraste de advisories antes de decidir la actualización, tal como se hizo para H-API-05.
- Prioridad propuesta: alta (incluida en la lista de 85%+ de cobertura/calidad del contrato, y ya estaba anotada como pendiente sin ID en la resolución de H-API-05).
- Contrato potencialmente afectado: ninguno de los endpoints cambia; es un cambio de versión de dependencia transitiva.
- Cómo validarlo: re-ejecutar `pip-audit -r api/requirements.txt` tras fijar `starlette>=1.3.1` (o la versión mínima que indique el advisory vigente) y confirmar que ya no reporta hallazgos para ese paquete; correr la suite de pruebas completa para descartar incompatibilidades de API entre versiones de Starlette.

### Archivos de requerimientos sin espacio de nombres por propietario
- Estado: CANDIDATO
- Evidencia: `api/app/uploads.py:43-49` (`store_requirement_file`) escribe en `Path(upload_dir) / file_name`, usando solo el nombre de archivo normalizado. `api/app/main.py:74-75` invoca esa función sin pasar el `owner`/identidad del token. No existe prueba que cubra dos usuarios subiendo un archivo con el mismo nombre.
- Impacto: dos identidades distintas que suban un archivo con igual nombre (p. ej. `requisitos.md`) sobrescriben silenciosamente el archivo del otro propietario, sin error, sin aviso y sin registro de cuál versión prevalece; esto es un problema de integridad de datos entre inquilinos (tenants), relacionado con la misma familia de riesgo que H-API-02 (autorización por identidad) pero no cubierto por esa corrección.
- Prioridad propuesta: media-alta (pérdida de datos entre usuarios, sin necesitar explotación activa — basta con coincidencia de nombre de archivo).
- Contrato potencialmente afectado: `POST /api/requirements` (forma de respuesta no cambiaría necesariamente, pero si se introduce una subcarpeta por owner, `storedAt` devuelto al cliente cambiaría de valor).
- Cómo validarlo: prueba de caracterización que suba el mismo nombre de archivo con dos tokens de distinto `owner` y verifique si el contenido del segundo sobrescribe al primero (hoy se espera que sí); luego diseñar la corrección (por ejemplo, subcarpeta por owner o nombre único) y repetir la prueba esperando que ambos archivos coexistan.

### Uso de API de ciclo de vida obsoleta (`on_event`)
- Estado: CANDIDATO
- Evidencia: `api/app/main.py:87` usa `@app.on_event("shutdown")`; al ejecutar `api/.venv/Scripts/python.exe -m pytest --cov=app --cov-report=term-missing` (2026-11-03) FastAPI emite `DeprecationWarning: on_event is deprecated, use lifespan event handlers instead` en cada una de las 32 pruebas.
- Impacto: bajo riesgo inmediato (las pruebas pasan y la app funciona), pero es deuda técnica concreta: una futura actualización mayor de FastAPI/Starlette puede remover `on_event` y romper el cierre ordenado de la conexión SQLite sin aviso previo más allá del warning actual.
- Prioridad propuesta: baja.
- Contrato potencialmente afectado: ninguno de los endpoints; es un detalle interno de inicialización/cierre de la aplicación.
- Cómo validarlo: migrar a un `lifespan` context manager (`@asynccontextmanager`) equivalente y volver a ejecutar la suite completa confirmando que ya no aparece el `DeprecationWarning` y que `close_connection` sigue invocándose al apagar la app (se puede verificar con una prueba que cierre el `TestClient` como context manager y confirme que la conexión queda cerrada).
