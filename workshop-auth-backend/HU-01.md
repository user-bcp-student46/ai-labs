# HU-01: Proteger el token de autenticación

## Origen

- **H-AUTH-03 — Token codificado en Base64 con secreto embebido** (Pendiente). Evidencia: `auth/src/main/java/com/bcp/workshop/auth/LegacyTokenUtil.java:8`, `auth/src/main/java/com/bcp/workshop/auth/LegacyTokenUtil.java:13`, `auth/src/main/java/com/bcp/workshop/auth/LegacyTokenUtil.java:14` y `auth/src/main/java/com/bcp/workshop/auth/LegacyTokenUtil.java:15`.
- **H-AUTH-04 — Secreto y política CORS configurados en código/propiedades fijas** (Pendiente). Evidencia: `auth/src/main/java/com/bcp/workshop/auth/LegacyTokenUtil.java:8`, `auth/src/main/resources/application.properties:4` y `auth/src/main/resources/application.properties:5`.

## Contexto

Como consumidor del servicio de autenticación, necesito que el token emitido al iniciar sesión tenga integridad verificable y que su material de firma y los orígenes CORS se configuren explícitamente, para evitar confiar en un token manipulable y limitar los orígenes autorizados. La matriz indica que el token actual solo está codificado en Base64 y que CORS permite ampliamente los orígenes. No especifica el formato de token que se adoptará ni la lista de orígenes autorizados.

## Ajustes necesarios

- Sustituir la generación casera del token por un mecanismo de firma criptográfica estándar; no incluir secretos fijos en el código ni en archivos versionados.
- Definir cómo se verifica la firma del token y acordar el formato con los consumidores antes de cambiarlo.
- Externalizar el secreto de firma y definir el comportamiento seguro cuando la configuración requerida no esté disponible.
- Sustituir el patrón CORS amplio por una lista explícita de orígenes aprobados. La lista debe acordarse antes de configurar la política.
- No registrar tokens ni material secreto; usar únicamente configuración y datos ficticios aislados en pruebas.

## Criterios de aceptación

- Una prueba confirma que un token emitido con configuración de prueba tiene una firma válida según el mecanismo acordado.
- Una prueba modifica el contenido de un token emitido y confirma que la verificación rechaza el token alterado.
- Una prueba confirma que la aplicación no emite tokens usando un secreto embebido cuando falta la configuración de firma.
- Las pruebas CORS confirman que un origen de la lista aprobada recibe el permiso esperado y que un origen fuera de esa lista no lo recibe.
- Una revisión automatizada de código y configuración confirma que no hay secretos de firma versionados ni tokens escritos en logs de prueba.

## Evidencia esperada

- Pruebas automatizadas de firma, rechazo de token alterado, configuración ausente y orígenes CORS permitidos/no permitidos, con sus resultados de ejecución.
- Diff revisado de la implementación y de la configuración externa, sin valores de tokens, secretos ni credenciales.
- Salida de JaCoCo con numerador, denominador y porcentaje del código modificado; meta mínima: 85%.
- Registro del acuerdo sobre formato/compatibilidad del token y lista de orígenes CORS autorizados.
